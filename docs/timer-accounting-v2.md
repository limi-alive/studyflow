# Timer accounting V2 — deployment prerequisite

**Do not deploy the V2 client before applying and reviewing `supabase/migrations/008_timer_accounting.sql`.** This PR does not execute the migration. Run it through the approved database change process; verify existing RLS and function grants in staging first. This migration adds `active_segments` and `checkpoint_minutes`, validates new writes, and replaces public/admin analytics RPCs with per-user interval union. No existing sessions, payouts or RLS policies are removed.

All monthly accounting uses Jalali months beginning at `Asia/Tehran` midnight. Calendar preference changes labels only. New Focus sessions record actual UTC active intervals; paused time is excluded. Overlapping intervals with distinct IDs are counted once per account in local monthly summaries after sync and in server analytics immediately after upload. Offline devices cannot know about another device until reconnection. Ties allocate time to the earlier interval/session ID, retaining all history rows. Legacy sessions have no pause timeline; their entire saved `study_seconds` remains attributed to their end month, and overlap with new intervals cannot be reliably deduplicated. Do not fabricate intervals for legacy rows.

Existing payout ledger entries are never changed. Historic Gregorian ledger entries overlapping a Jalali month are conservatively reserved against new payouts. An administrator must reconcile any ambiguous historical entitlement before paying; never automatically pay or undo a prior payout based only on calendar conversion.

Sync conflicts for the same ID with different source content stop with `session-conflict-needs-review` and keep the local row. The UI retries with a foreground/background schedule; a conflicting row needs manual reconciliation rather than a destructive overwrite. Device clock changes can still shift timestamps; a checkpoint caps unattended credit, but authoritative clock validation would require a server-assisted online flow.

**Rollback:** Restore the previous client and the RPC definitions from migrations 005 and 007 in a reviewed follow-up change. Keep both new columns and existing segment data; dropping them would destroy source history. Do not revert or modify payout records or historical sessions. Once segment-based sessions exist, reverting the RPCs will change displayed period totals; coordinate a maintenance window and take an authorized private backup first.
